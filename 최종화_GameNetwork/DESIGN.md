# DESIGN.md

# 1. 문서 개요

이 문서는 네트워크 프로그래밍 학습을 위해 구현하는 두 프로젝트의 설계와 통신 방식을 설명한다.

| 프로젝트 | 개발 환경 | 주요 목적 |
|---|---|---|
| CoinGame | Unity 6, C# | 서버 권한 기반 멀티플레이 게임 구현 |
| UdpPeerPosition | .NET 10, C# | UDP를 이용한 두 피어 간 좌표 교환 |

두 프로젝트는 네트워크 통신을 다룬다는 공통점이 있지만, 목적과 구조가 다르다. CoinGame은 게임 서버가 게임 상태를 검증하고 동기화하는 구조이며, UdpPeerPosition은 두 프로그램이 서로의 좌표 메시지를 직접 교환하는 구조다.

# 2. CoinGame

## 2.1 프로젝트 개요

CoinGame은 Unity와 Netcode for GameObjects(NGO)를 사용하여 구현하는 로컬 멀티플레이 게임이다.

플레이어는 Host 또는 Client로 접속해 캐릭터를 이동시키고 코인을 획득한다. 코인 생성, 획득 가능 여부 검증, 점수 변경 등 중요한 게임 상태는 서버가 관리한다.

### 개발 환경

| 항목 | 설정 |
|---|---|
| 엔진 | Unity 6 |
| 네트워크 라이브러리 | Netcode for GameObjects 2.13.3 |
| 전송 계층 | Unity Transport |
| 입력 | Input System |
| UI | UGUI |
| 캐릭터 이동 | CharacterController |
| 테스트 주소 | 127.0.0.1 |
| 테스트 포트 | 7777 |
| 접속 방식 | Host / Client |

## 2.2 핵심 설계 원칙

### 서버 권한

게임의 중요한 상태는 서버가 최종적으로 결정한다.

- 플레이어의 이동 결과
- 코인의 생성 및 제거
- 코인 획득 가능 여부
- 플레이어별 점수
- 코인과 관련된 게임 상태

클라이언트는 입력이나 요청을 서버에 전달할 수 있지만, 요청만으로 점수나 코인 상태를 임의로 변경할 수 없어야 한다.

### 책임 분리

각 컴포넌트는 명확한 책임을 갖도록 구성한다.

- 네트워크 시작 및 접속 UI: Host/Client 연결 요청과 상태 표시
- 플레이어 입력: 로컬 플레이어의 입력 수집
- 플레이어 이동: 서버에서 이동 처리 및 결과 반영
- 플레이어 상태: 점수 등 네트워크 동기화 데이터 관리
- 코인 관리: 코인 생성, 유효성 검사, 획득 처리 및 제거
- UI: 점수와 연결 상태 등 사용자에게 필요한 정보 표시

컴포넌트 간 직접적인 의존성을 최소화하고, 새로운 기능을 추가하더라도 기존 시스템의 수정 범위를 줄이는 것을 목표로 한다.

## 2.3 네트워크 구성

Host는 서버와 클라이언트 역할을 함께 수행한다. Client는 서버에 접속하여 게임에 참여한다.

로컬 테스트에서는 다음 주소를 사용한다.

- 서버 주소: `127.0.0.1`
- 서버 포트: `7777`

Host와 Client를 각각 실행하여 연결, 이동, 코인 획득 및 점수 동기화를 확인한다.

## 2.4 플레이어 이동

플레이어 이동은 `CharacterController`를 사용한다.

기본적인 입력 처리 흐름은 다음과 같다.

1. 소유한 플레이어의 입력을 수집한다.
2. 입력 정보를 서버에 전달한다.
3. 서버가 이동을 처리하고 유효한 이동 결과를 결정한다.
4. `NetworkTransform` 등 네트워크 동기화 기능을 통해 다른 클라이언트에 이동 결과를 전달한다.

클라이언트가 임의로 서버의 이동 결과를 확정하지 않도록 서버 권한 구조를 유지한다.

초기 구현에서 프레임별 이동 요청을 전송하는 구조를 사용했다면, 이후에는 불필요한 RPC 호출을 줄이고 이동 입력의 전송 빈도와 동기화 방식을 검토할 수 있다.

## 2.5 코인 생성 및 획득

코인의 생성과 획득 처리는 서버가 담당한다.

### 코인 생성

- 코인은 서버에서 생성한다.
- 네트워크에 등록된 코인 오브젝트를 사용한다.
- 코인의 생성과 제거 상태는 참여 중인 클라이언트에 동기화한다.

### 코인 획득

코인 획득은 클라이언트의 요청과 서버의 판정으로 나뉜다. 코인에 닿았을 때도 클라이언트는 요청만 보내고, 점수와 코인 제거는 서버가 결정한다.

| 역할 | 담당 | 내용 |
|---|---|---|
| 입력 | `NetworkCoinCollector.Update` (소유자만) | 접촉: 수평 거리 1.0 이내 코인을 코인당 한 번 자동 요청, `E`: 가장 가까운 코인, `F1`~`F4`: 시험용 요청 |
| 통신 요청 | `RequestCollectCoinRpc(coinId)` (`SendTo.Server`) | 코인 ID만 보낸다. 점수나 코인 제거는 보내지 않는다. |
| 서버 판정 | `NetworkCoinSpawner.TryCollectCoin` | 아래 규칙으로 결과 결정 |
| 상태 반영 | 서버 | `Score` NetworkVariable 증가, 코인 Despawn, 3초 뒤 새 코인 생성 |
| 결과 전달 | `CollectResultRpc(coinId, result)` (`SendTo.Owner`) | 요청한 플레이어에게만 결과 전달 |
| 화면 표시 | `NetworkScoreUI` | 점수, 남은 코인 수, 내 요청 결과 최근 5건 |

코인 식별값은 서버가 생성 순서대로 붙이는 정수 `CoinId`(1부터 증가)다. `NetworkObjectId`는 NGO가 재사용할 수 있기 때문에, 획득된 코인과 새 코인이 같은 값을 받지 않도록 별도 ID를 둔다. 서버는 세션 동안 `activeCoins`(ID → 코인)와 `collectedCoinIds`(획득된 ID 집합)를 보관한다.

서버 검사 규칙 (위에서부터 순서대로):

1. RPC를 보낸 클라이언트가 해당 플레이어의 소유자가 아니면 처리하지 않는다.
2. `activeCoins`에 없는 ID이고 `collectedCoinIds`에 있으면 `AlreadyCollected`로 거절한다.
3. `activeCoins`에도 `collectedCoinIds`에도 없으면 `InvalidCoinId`로 거절한다.
4. 서버의 플레이어 위치와 코인 사이 수평 거리가 `pickupRange`(1.5)를 넘으면 `TooFar`로 거절한다.
5. 통과하면 ID를 `activeCoins`에서 빼서 `collectedCoinIds`에 넣는다. 그다음 점수를 올리고 코인을 제거한 뒤 `Accepted`를 돌려준다.

NGO는 서버에서 RPC를 하나씩 순서대로 처리한다. 5단계에서 첫 요청이 ID를 바로 옮기므로, 같은 코인에 대한 두 번째 요청(같은 플레이어의 중복 요청이든 다른 플레이어의 동시 요청이든)은 2단계에서 `AlreadyCollected`가 된다. 따라서 보상은 한 번만 지급된다.

## 2.6 점수 및 상태 동기화

점수는 플레이어별로 관리한다.

- 점수의 최종 변경 권한은 서버에 있다.
- 클라이언트는 서버가 확정한 점수를 표시한다.
- 한 플레이어의 점수 변경이 다른 플레이어의 개인 점수를 덮어쓰지 않아야 한다.
- 코인의 생성, 획득, 제거 상태는 네트워크를 통해 동기화한다.

이 프로젝트는 개인별 점수를 사용하는 구조이며, 별도의 승리 또는 패배 조건은 정의하지 않는다.

## 2.7 재접속 정책

재접속 시 기존 개인 점수를 유지하지 않고 초기화한다.

재접속은 새로운 접속 세션으로 취급하며, 플레이어가 다시 참여하면 초기 상태에서 게임을 진행한다.

이 정책에 따라 다음 항목을 확인한다.

- 연결 종료 시 플레이어 관련 네트워크 오브젝트가 적절히 정리되는지 확인한다.
- 재접속 시 플레이어가 정상적으로 생성되는지 확인한다.
- 이전 세션의 점수가 새 세션에 남아 있지 않은지 확인한다.
- 코인 상태와 플레이어 상태가 서로 일치하는지 확인한다.

## 2.8 주요 테스트 항목

- Host 시작 및 Client 접속
- 플레이어 이동과 다른 클라이언트에서의 위치 동기화
- 서버의 코인 생성 및 전체 클라이언트 표시
- 정상적인 코인 획득과 점수 증가
- 잘못된 코인 ID 요청 거부
- 획득 가능한 거리보다 먼 위치에서의 요청 거부
- 동일 코인에 대한 중복 획득 요청 방지
- 여러 플레이어의 개인 점수 분리
- 연결 종료와 재접속 후 상태 초기화
- 비정상 요청과 네트워크 오류 처리

잘못된 코인 ID와 거리 검증은 별도로 시험하여 서버가 잘못된 요청을 거부하는지 확인해야 한다. 해당 테스트를 수행하기 전에는 검증 기능이 완전히 확인되었다고 판단하지 않는다.

# 3. UdpPeerPosition

## 3.1 프로젝트 개요

UdpPeerPosition은 C#/.NET 10으로 구현하는 콘솔 애플리케이션이다.

두 피어가 UDP로 2D 정수 좌표를 교환한다. 각 피어는 자신의 좌표를 유지하면서 상대 피어의 최신 좌표를 별도로 저장하고 표시한다.

### 개발 환경

| 항목 | 설정 |
|---|---|
| 언어 | C# |
| 런타임 | .NET 10 |
| 통신 프로토콜 | UDP |
| 메시지 형식 | JSON |
| 테스트 주소 | 127.0.0.1 |
| Peer A 로컬 포트 | 5000 |
| Peer B 로컬 포트 | 5001 |

## 3.2 네트워크 설정

| 항목 | Peer A | Peer B |
|---|---|---|
| Peer ID | A | B |
| 로컬 주소 | 127.0.0.1 | 127.0.0.1 |
| 로컬 포트 | 5000 | 5001 |
| 상대 Peer ID | B | A |
| 상대 포트 | 5001 | 5000 |

두 피어는 같은 PC에서 서로 다른 포트를 사용하여 실행할 수 있다.

## 3.3 메시지 설계

위치 메시지는 JSON으로 직렬화한다.

| 필드 | 자료형 | 설명 |
|---|---|---|
| `PeerId` | string | 메시지를 보낸 피어의 ID |
| `Sequence` | long | 메시지 순서 번호 |
| `X` | int | X 좌표 |
| `Y` | int | Y 좌표 |

메시지 예시:

```json
{
  "PeerId": "A",
  "Sequence": 1,
  "X": 3,
  "Y": 5
}
```

새로운 위치 메시지를 생성할 때마다 순서 번호를 증가시킨다. 기존 메시지를 재전송하는 경우에는 원래의 순서 번호와 좌표를 유지한다.

## 3.4 송신 처리

각 피어는 자신의 위치를 변경하거나 현재 위치를 전송할 수 있다.

- `move X Y`: 좌표 변경 후 새로운 위치 메시지 전송
- `send`: 현재 좌표를 새로운 순서 번호로 전송
- `replay N`: 기존 메시지 N을 동일한 내용으로 재전송
- `bench N`: N개의 위치 메시지를 연속 전송

송신 완료 호출 수와 송신 오류 수를 별도로 집계한다.

UDP 송신 호출의 완료는 상대 피어가 해당 메시지를 수신했다는 보장이 아니다.

## 3.5 수신 처리

수신은 `ReceivePositionsAsync()`에서 비동기적으로 처리한다. 따라서 콘솔 입력을 기다리는 동안에도 상대 피어의 메시지를 받을 수 있다.

수신 메시지는 다음 순서로 검사한다.

1. 송신 주소와 포트 확인
2. 빈 메시지 확인
3. JSON 역직렬화
4. 피어 ID와 순서 번호 검증
5. 마지막 반영 순서 번호와 비교
6. 상대 좌표 및 마지막 반영 순서 번호 갱신

빈 메시지, 잘못된 JSON, 유효하지 않은 필드, 오래된 메시지 및 중복 메시지는 무시한다.

## 3.6 순서 번호 처리

수신한 메시지의 순서 번호가 마지막으로 반영한 번호보다 작거나 같으면 해당 메시지를 무시한다.

예를 들어, 순서 번호 2의 좌표를 이미 반영했다면 순서 번호 1이 나중에 도착하더라도 상대 좌표를 이전 상태로 되돌리지 않는다.

이 기능은 UDP에서 발생할 수 있는 중복 수신과 순서가 뒤바뀐 메시지로 인해 최신 상태가 잘못 덮어써지는 문제를 방지한다.

## 3.7 위치 표시

`show` 명령은 자신의 좌표와 상대 피어의 마지막으로 반영된 좌표를 표시한다.

상대 위치를 아직 수신하지 않았다면 `Not received yet`으로 표시한다.

수신한 데이터그램 수, 반영된 위치 메시지 수, 잘못된 메시지 수, 오래되거나 중복된 메시지 수는 `stats` 명령으로 확인한다.

## 3.8 전송량 테스트

수신 측에서 `benchstart N`으로 측정을 시작하고, 송신 측에서 `bench N`으로 메시지를 전송한다. 송신이 끝나면 수신 측에서 `benchstop`으로 측정을 종료한다.

측정 항목은 다음과 같다.

- 요청한 송신 메시지 수
- 송신 완료 호출 수
- 송신 오류 수
- 측정 구간 내 수신 데이터그램 수
- 측정 종료 시점의 관측 누락 수
- 송신 소요 시간
- 수신 측 측정 구간 시간

### 테스트 결과

| 항목 | 100개 테스트 | 10,000개 테스트 |
|---|---:|---:|
| 요청 메시지 수 | 100 | 10,000 |
| 송신 완료 호출 수 | 100 | 10,000 |
| 송신 오류 수 | 0 | 0 |
| 수신 데이터그램 수 | 100 | 10,000 |
| 측정 종료 시점의 관측 누락 수 | 0 | 0 |
| 송신 소요 시간 | 24.00 ms | 145.73 ms |
| 수신 측 측정 구간 시간 | 57,391.57 ms | 15,000.10 ms |

### 결과 해석

두 테스트 모두 송신 완료 호출 수와 수신 측에서 관측한 데이터그램 수가 요청 메시지 수와 일치했다. 관측 누락 수와 송신 오류 수는 모두 0이었다.

단, 수신 측 측정 시간에는 측정 시작 및 종료 명령을 입력하는 데 걸린 시간과 터미널 전환 시간이 포함된다. 따라서 이 시간은 순수 네트워크 지연 시간이나 실제 수신 처리 시간으로 해석할 수 없다.

또한 UDP는 전달을 보장하지 않는다. 이번 결과는 지정된 로컬 테스트 환경에서 관측한 결과이며, 모든 네트워크 환경에서 손실이 발생하지 않는다는 의미는 아니다.

## 3.9 주요 테스트 항목

- Peer A와 Peer B 간 정상 좌표 전송
- 자신의 좌표와 상대 좌표가 독립적으로 유지되는지 확인
- 정상적인 순서 번호 증가 확인
- 오래된 메시지 재전송 후 무시되는지 확인
- 중복 메시지 재전송 후 무시되는지 확인
- 빈 메시지와 잘못된 JSON 처리
- 유효하지 않은 피어 ID 및 순서 번호 처리
- 100개 메시지 전송량 테스트
- 10,000개 메시지 전송량 테스트
- 누적 송수신 통계 확인

# 4. 두 프로젝트의 설계 차이

| 비교 항목 | CoinGame | UdpPeerPosition |
|---|---|---|
| 주요 목적 | 멀티플레이 게임 구현 | 피어 간 좌표 메시지 교환 |
| 통신 구조 | NGO 기반 클라이언트-서버 | UDP 기반 피어 간 직접 송수신 |
| 상태 결정 | 서버 권한 | 각 피어가 자신의 상태를 유지 |
| 메시지 처리 | RPC 및 네트워크 동기화 | JSON 데이터그램 |
| 주요 상태 | 플레이어 이동, 코인, 점수 | 피어 ID, 순서 번호, 좌표 |
| 유효성 검사 | 서버에서 게임 규칙 검증 | 수신 측에서 메시지와 순서 번호 검증 |
| 테스트 초점 | 권한, 게임 상태 동기화, 중복 요청 방지 | 송수신, 순서 처리, 전송량 측정 |

CoinGame에서는 클라이언트가 요청하더라도 서버가 게임 규칙에 따라 유효성을 검증하고 상태를 확정한다.

반면 UdpPeerPosition에서는 각 피어가 상대 메시지를 수신하고 순서 번호를 검사하여 상대 좌표를 갱신한다. 이 프로젝트는 게임 서버의 권한 구조를 구현하는 것이 아니라, UDP 통신과 메시지 처리 원리를 학습하는 데 목적이 있다.

# 5. 향후 검증 및 개선 사항

## CoinGame

- 잘못된 코인 ID 요청에 대한 서버 검증 테스트
- 허용 거리 밖에서의 코인 획득 요청 테스트
- 중복 요청에 따른 점수 중복 증가 방지 확인
- Host/Client 이동 및 상태 동기화 테스트
- 재접속 시 개인 점수 초기화 확인
- 연결 종료와 비정상 요청에 대한 예외 처리 검증

## UdpPeerPosition

- 잘못된 JSON 및 필드 값 테스트
- 순서 번호가 뒤바뀐 메시지 테스트
- 중복 메시지 처리 테스트
- 더 다양한 전송량에서의 관측 결과 기록
- 실제 LAN 환경에서의 추가 테스트
- 수신 측 측정 구간과 송신 측 측정 구간을 구분한 성능 측정 개선

# 6. 결론

CoinGame은 서버 권한, 게임 규칙 검증, 플레이어 상태 및 점수 동기화에 중점을 둔다. UdpPeerPosition은 UDP 데이터그램 송수신, JSON 메시지 처리, 순서 번호 검증 및 전송량 측정에 중점을 둔다.

두 프로젝트를 통해 네트워크 메시지를 전달하는 기본 원리부터 서버가 게임 상태를 안전하게 관리하는 방식까지 단계적으로 학습할 수 있다.

문서에 기록된 테스트 결과는 실제 수행한 테스트의 관측값을 기준으로 하며, 아직 검증하지 않은 기능은 완료된 것으로 간주하지 않는다.
